# AIHOT 就业趋势项目：五人开发分工与七天并行排期

> 版本：v2.0（开发执行版）  
> 日期：2026-11-16  
> 依据：[ROADMAP.md](../ROADMAP.md)  
> 团队规模：5 人  
> 开发策略：**先跑通端到端最短链路，再集中调优；先真实数据闭环，再完善体验**  
> 交付节奏：D1–D3 快速实现，D4–D5 调优，D6–D7 冻结与验收

## 1. 开发策略：两段式交付

### 1.1 两段式目标

| 阶段 | 目标 | 完成标志 |
|---|---|---|
| D1–D3：快速实现 | 最短链路跑通 | 3 家公司 + 2 个政策源 → 数据入库 → 指标 API → 看板可点通 |
| D4–D5：集中调优 | 提升准确性和演示质量 | 去重、技能词表、指标边界、页面体验、关键测试和真实备份完成 |
| D6–D7：冻结交付 | 不再加功能 | 验收、文档、排练和现场降级方案完成 |

**D3 结束即冻结主链路。** D4 之后只能优化既有能力，不能新增行业、账号体系、复杂模型或页面大改。

### 1.2 快速实现阶段允许做的事

- 3 家招聘公司和 2 个政策源先直接写进配置，不做通用信源管理界面。
- 职位先使用“当前态宽表 + 原始 JSON”，不急着拆公司、城市、技能维度表。
- 技能先用规则和词典提取，人工抽查；不在第一版训练模型。
- 政策继续复用 AIHOT 现有采集、摘要和 publication 链路，不重写内容系统。
- 看板只做评审主线需要的指标和筛选，不做完整运营后台。
- 测试优先覆盖去重、字段归一化、指标公式和主链路 smoke，其余在调优阶段补齐。
- 页面可以在 D1–D2 使用明确标记的临时数据搭骨架，但**最终演示只允许真实数据或明确标记的人工核验导入**。

### 1.3 调优阶段才做的事

- 提高字段抽取覆盖率、减少重复职位和技能同义词漏识别。
- 优化指标边界、空数据、未知字段、样本覆盖说明和证据追溯。
- 优化查询索引、API 响应、桌面/大屏/手机显示和异常状态。
- 补关键单元测试、浏览器验收、真实数据备份和性能问题。
- 调整措辞、图表可读性和 5 分钟演示路径。

### 1.4 任何阶段都不能妥协

- 不伪造职位、政策、发布时间、历史快照和采集日志。
- 每个趋势数字必须能回到职位 ID、观测记录或政策原文。
- 单次快照不能包装成长期趋势；政策与岗位只能表达共同方向，不能宣称因果。
- 不绕过登录、验证码、反爬和付费墙；不提交密钥、`.env` 和个人数据。
- 不修改 AIHOT 核心发布链路来走捷径；招聘数据留在自己的模块中。

## 2. 五人开发角色

| B | 数据源开发 | 爬虫、HTTP、Playwright、网页解析 | 3 家公司招聘采集和 2 个政策源接入 | C |
| C | 数据治理与指标 | SQL、数据清洗、分类词典、指标设计 | 归一化、去重、技能词典、指标口径和校验 | D |
| D | 后端与 API | TypeScript、Fastify、PostgreSQL、pg-boss | 模块后端、迁移、队列、API、建议规则、后端测试 | C |
| E | 前端开发 | React、React Router、SSR、数据可视化 | 看板、筛选、证据交互、响应式和前端验收 | A |

姓名与 GitHub 账号在 D1 前两小时填入团队群或本文末尾。角色按实际能力认领，不根据账号名分配。

### 2.1 最短数据链与责任边界

招聘主线：

`官方招聘页 → B 原始采集 → C 归一化/去重 → D 入库与 API → E 页面证据`

政策主线：

`政府官方页 → B 信源接入 → AIHOT 政策处理/publication → E 政策卡片与岗位方向对照`

责任边界：

- **B 负责“拿得到、拿得对、留证据”**，不决定趋势指标和页面样式。
- **C 负责“字段统一、去重可信、公式可解释”**，不私自新增采集源。
- **D 负责“存得住、查得快、接口稳定”**，不擅自改变指标口径。
- **E 负责“看得懂、点得回、演示稳”**，不在前端重复计算后端指标。
- **A 负责“接口对齐、及时合入、环境可跑、阻塞清除”**，不代替四个人完成各自专业任务。

## 3. 代码与文件归属

| 角色 | 主要工作范围 | 说明 |
|---|---|---|
| A | `site/modules/` 注册、`site/package.json`、Dockerfile、部署与环境配置、集成脚本 | 这些共享入口只由 A 修改，避免冲突 |
| B | `modules/career-insights/collector/`、招聘/政策源配置和采集说明 | 每个来源独立适配器，输出统一原始结构 |
| C | `modules/career-insights/data/`、技能词典、指标规范和数据校验脚本 | 不直接改 HTTP 路由和共享注册文件 |
| D | `modules/career-insights/module.ts`、`server.ts`、`migrations/`、队列、API、后端测试 | 负责模块骨架和对外接口 |
| E | `modules/career-insights/web/`、模块页面声明所需的页面文件 | 只通过 HTTP API 读数据，不访问数据库和密钥 |

规则：跨角色需要修改对方文件时，先通知文件负责人；共享入口的最终修改由 A 完成。

## 4. D1 必须冻结的四份接口

快速开发最怕“人人都在等字段”。D1 上午先定接口，下午各线并行。

### 4.1 `NormalizedJob`：B → C/D

必须包含：

`source_key`、`job_key`、`title`、`official_url`、`company_name`、`role_family`、`locations`、`degree`、`experience`、`employment_type`、`skills`、`published_at`、`raw`、`fetched_at`

要求：

- `job_key` 优先取官方职位 ID，否则使用规范化 URL 哈希。
- 抓不到的值写空，不猜测；不得用采集时间冒充发布时间。
- `skills` 可以暂为空数组，但必须能追溯到原始内容。

### 4.2 数据库与观测

C 给出字段和去重规则，D 落地两张表：

- `career_jobs`：职位当前态。
- `career_job_observations`：每次成功采集的观测记录。

D1 只定义当前真正要用的字段。不要提前创建后台配置、公司维度、技能维度、预测结果等第一周用不到的表。

### 4.3 `MetricSpec`：C → D/E

每个指标必须写清：

- `metric_id`：稳定标识。
- 中文名称和一句话解释。
- 分子、分母、时间窗和去重口径。
- 缺失值、未知值和空数据的处理。
- 证据类型：职位 ID、观测 ID、政策 ID 或官方链接。
- 页面必须同时显示的样本限制。

第一版只做：岗位结构、技能需求占比、应届友好占比、观察窗新增职位，以及政策—岗位共同方向。

### 4.4 API 契约：D → E

D1 末给出 v0，D2 末冻结 v1：

- `GET /api/site/career-insights/summary`
- `GET /api/site/career-insights/jobs`
- `GET /api/site/career-insights/jobs/:id`

每个响应需包含 `as_of`、样本量、来源覆盖、算法/词典版本和 evidence ID。错误响应要区分无数据、参数错误和内部错误。

接口变更必须在团队频道通知 A、C、E；D3 后只允许字段错误修复，不改变指标含义。

## 5. 七天并行开发排期

### D1：环境、契约和各线最小可运行件

- **A：** 检查 Node/Docker/PostgreSQL/模型配置；建立 `feat/integration` 集成分支；创建五人分支；完成空模块注册和启动验证。
- **B：** 试抓 1 家公司官方招聘页和 1 个政策来源；产出原始样本、页面结构、访问限制和官方链接。单来源超过 2 小时即换备选。
- **C：** 写出 `NormalizedJob` 字段、去重键、未知值规则和四类指标的初版口径；用 B 的样本做一次归一化草稿。
- **D：** 建模块骨架、两张表迁移、空队列和 API stub；先用最小数据返回结构，不等待最终字段。
- **E：** 复用 AIHOT 页面框架搭看板骨架；用带“临时数据”标记的样例验证布局，不接正式数据。

**D1 结束标志：**

- 本地或 Docker 有一条可启动路径。
- 四份接口有 v0。
- 1 家公司 + 1 个政策源已有真实原始样本。
- 五人任务都已推进，没有人因等待接口停摆。

### D2：打通一条最短真实链路

- **A：** 将 B/C/D/E 的最小增量合入集成分支；解决契约冲突；跑一次环境级 smoke；打通“1 家公司真实职位 → 数据库 → API → 页面”。
- **B：** 扩展到 3 家公司适配器，并接入 2 个政策源；统一失败日志和数据来源字段。
- **C：** 完成职位归一化、去重和首版技能词典；给 D 提供可直接入库的数据结构；验证重复采集不重复。
- **D：** 完成持久化、采集队列、summary/jobs API 和 evidence ID；补空数据与错误响应。
- **E：** 接入真实 API，完成总览、基础筛选和职位证据展开；删除临时数据路径。

**D2 结束标志：**

- 至少 1 家公司、1 个政策源、1 个指标、1 个职位证据能完整点通。
- 同一招聘来源连续采集两次不产生重复职位。
- API 契约冻结为 v1。

### D3：MVP 主链路冻结

- **A：** 合并全部主线功能；完成一次从采集到页面的端到端演示；冻结页面、接口和指标范围。
- **B：** 完成 3 家公司和 2 个政策源的真实接入；输出来源覆盖、条数、失败原因和证据表。
- **C：** 完成四类指标和政策—岗位共同方向；抽查去重、技能归一化和未知字段；输出样本限制。
- **D：** 完成规则建议接口、指标查询、证据返回和关键后端测试；保证无效参数和空数据不崩。
- **E：** 完成主路径、筛选、建议和证据展开；桌面和手机至少各走一遍。

**D3 结束标志：**

- 3 家公司 + 2 个政策源可重复采集。
- 四项指标和一个政策共同方向来自真实数据。
- 评审主路径完整可点，所有数字可回证据。
- **停止新增功能，进入调优阶段。**

### D4：集中调优数据、指标和界面

- **A：** 建立 P0 缺陷清单；每天只批准调优项；处理部署、备份和跨线阻塞。
- **B：** 修复字段缺失、来源失败和重复页问题；提高有效职位覆盖率；不增加新公司，除非替换失败来源。
- **C：** 修正误去重、技能同义词漏识别、未知值比例和指标边界；输出前后对比。
- **D：** 加索引、修慢查询、统一错误格式；补指标、去重和证据链接测试。
- **E：** 优化筛选、证据展开、空态/错误态、长文本、大屏和手机显示；不重做设计体系。

**D4 原则：** 任何优化必须回答“它改善了哪个演示或数据问题”，否则不做。

### D5：第二次真实采集与交付调优

- **A：** 跑类型检查、后端测试、Web 构建、迁移检查和 smoke；生成真实数据备份；冻结演示版本。
- **B：** 执行第二次真实采集；导出来源证据表和采集日志；验证政策与职位链接仍然有效。
- **C：** 对比两个观测时点，检查变化是否能解释；无法解释的变化只展示观测事实，不生成趋势结论。
- **D：** 完成后端和迁移检查；修复阻塞演示的 P0 技术问题。
- **E：** 完成浏览器验收、截图/录屏兜底和真实备份页面核对。

**D5 结束标志：**

- 两个真实观测时点存在。
- 关键检查通过，真实备份可恢复。
- 断网时仍可展示本地网站和真实数据。
- 不再接受新功能。

### D6：验收与复现

- **A：** 按路线图验收清单逐项核对；让另一名成员独立按文档启动；冻结代码和数据。
- **B：** 完成来源与方法说明、采集失败排查和 5 条政策问答。
- **C：** 完成字段、去重、技能词典和指标口径说明，标清样本限制。
- **D：** 完成迁移、API、指标公式和故障排查说明。
- **E：** 完成最终浏览器走查、演示截图/录屏和大屏显示检查。

**D6 结束标志：** 另一名成员可以独立完成 5 分钟演示；只允许修阻塞缺陷。

### D7：排练与现场准备

- **A：** 两轮计时排练；冻结版本；准备现场网络失败卡和本地启动步骤。
- **B：** 演练政策证据和来源合规问答。
- **C：** 演练指标口径、去重和样本限制问答。
- **D：** 演练本地启动、数据库和 API 故障处理。
- **E：** 演练页面操作、备用截图/录屏和投影显示。

## 6. 并行协作规则

### 6.1 分支与合并

| 角色 | 分支 | 合并目标 |
|---|---|---|
| A | `feat/integration` | `main`，由 A 统一合入 |
| B | `feat/career-collector` | `feat/integration` |
| C | `feat/career-data-metrics` | `feat/integration` |
| D | `feat/career-api` | `feat/integration` |
| E | `feat/career-dashboard` | `feat/integration` |

- 每人只在自己的分支提交，不直接推 `main`。
- 每个 Pull Request 只做一类事：采集、数据、API 或页面。
- A 每天至少合并一次可用增量；冲突由文件负责人处理，A 不代写业务逻辑。
- PR 必须写：改了什么、如何验证、影响了谁、还缺什么。
- D3 后只提交修复和调优 PR，标题注明对应缺陷或指标。

### 6.2 每日节奏

| 时间 | 动作 | 参与者 |
|---|---|---|
| 上午开始，10 分钟 | 对齐今天各自交付、接口和阻塞 | 全队 |
| 中午 | C/D/E 对齐字段和 API；B/C 对齐数据质量 | B、C、D、E |
| 下午 | A 合入可用增量并跑主链路 | A |
| 结束前，20 分钟 | 五人各用 1–2 分钟展示当天真实增量 | 全队 |

阻塞超过 30 分钟必须升级给 A；不允许一个人静默卡住整条链路。

### 6.3 代码审查

- A 审查共享注册、部署、环境变量和跨模块改动。
- D 审查数据入库、API 和迁移；C 审查字段、去重和指标口径。
- E 的页面至少由 A 或 D 做一次主路径验收。
- 快速阶段审查以“能跑、契约对、无假数据”为标准；调优阶段再补边界和测试质量。

## 7. 调优优先级与止损

### 7.1 D4–D5 调优优先级

1. 数据真实性、去重错误和证据断链。
2. 指标公式、未知值处理和页面口径不一致。
3. 主路径失败、空数据白屏、API 超时。
4. 技能词典、字段覆盖和样本展示。
5. 视觉、动效和次要交互。

### 7.2 立即停止并降级的情况

- 单个招聘源超过 2 小时仍无法稳定采集：换备选来源。
- 3 家公司不足：保留真实自动来源，其他使用明确标记的人工核验导入，不冒充自动采集。
- 第二次采集失败：只展示一个观测时点，隐藏涨跌。
- 指标无法解释：先删指标，不硬编结论。
- 页面拖慢主链路：先保证真实数据和证据，削减次要图表。

### 7.3 人员不足时

- 4 人：B 兼政策来源，C 兼部分前端数据绑定，取消所有 P1。
- 3 人：A 负责集成与政策接入，B 负责采集，D 负责后端和指标；E 的工作由 A/D 分担，只保留一个看板页面。
- 任何情况下都不能通过伪造数据或跳过证据链来“赶上进度”。
